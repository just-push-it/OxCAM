# ADR-0003: Generated toolpaths saved with the project

- **Status:** accepted
- **Date:** 2026-10-21

## Context

Reopening a project generated every operation again: about 100 s for the maintainer's flange
(two 3D roughing operations, a contour, flat finishing). Rest machining made it worse, because it
generated every earlier operation of the setup once more to simulate the stock it starts from.
Toolpaths depend on the program version as well as on the project: a release whose strategies
cut differently must not show toolpaths from the release before it.

## Decision

### One cache, keyed by the inputs

`ToolpathCache` (libs/document) holds generated toolpaths by operation and input key. The key
is `toolpathInputKey`: a SHA-256 of everything the toolpath depends on (the operation, its setup,
tools and models, the earlier operations for rest machining), the program version and
`kToolpathRevision`. A revision bump, or a new version, changes every key, so old toolpaths
simply stop matching and are generated again. Nothing has to be cleaned up or migrated.

`cachedToolpath(doc, setup, op)` returns the cached toolpath for the current key or generates
it and stores it. The GUI's background generation, posting, rest machining's in-process stock,
the setup simulation and the CLI all go through it. A toolpath is generated by one thread at a
time: another thread asking for it (a post while the GUI is still generating) waits for that
generation instead of starting its own, and can still be cancelled. A document's snapshots (for background work) share
its cache, which is thread-safe. A few keys are kept per operation, so undoing an edit finds
the toolpath of the inputs before it. Failures are not cached.

### In the archive

`Document::save` writes `cache/toolpaths.json` into the `.ocam` archive:
`{"format": "oxcam.toolpath-cache", "version": 1, "entries": [{operation, key, toolpath}]}`,
one entry per enabled operation whose cached toolpath matches its current key. Toolpaths use
the toolpath JSON of the golden files, rounded to 1e-6 mm. `Document::open` loads it. The cache is
optional: a missing, damaged or other-version cache, or an entry that does not read, means
those toolpaths are generated again. Opening never fails because of it.

### The stock is cached on the user's machine, not in the project

*Amended 2026-10-30.* The simulated stock (tri-dexel grids after every operation) is not stored
in the project: a setup's stocks are megabytes even compressed (12 to 15 MB for each of the
flange's setups) and would weigh on every save. The first version of this ADR said simulating
was cheap enough (about 2 s for the flange); with finer resolutions, smooth display and stock
carried from earlier setups it grew to two and nine minutes for the flange's two setups.

So the GUI keeps whole-setup simulations in a local cache: one file per simulation in the user's
cache folder (`QStandardPaths::CacheLocation`/simulations, `<key>.oxsim`), named by its
`simulationInputKey`, which covers the program version, the setup, its stock sources, the
toolpaths and the simulation's options. The file (`encodeSimulation`, libs/document/SimulationCache) holds the
stocks after every operation (stock tiles shared between checkpoints are written once), the
collisions, the comparison and the toolpaths, compressed, and `kSimulationCacheVersion`: whoever
changes what a simulation outputs for the same inputs raises it, as `kToolpathRevision`. What is
cheap to derive (the machine, tool shapes) comes from the document on reading. A file under
another key or version, or damaged, is ignored and the setup is simulated again. The folder is
capped at 4 GB, least recently used removed first. `OXCAM_SIMULATION_CACHE` names another
folder, or `none` to turn the cache off (the GUI tests do).

On opening a project the GUI prepares every setup's simulation in the background, one at a
time, after the toolpaths are generated, so every operation's in-process stock is there when it
is clicked. Asking for a setup that is being prepared waits for that preparation.

*Amended 2026-11-01.* A simulation also keeps a key for each of its stocks (`stockInputKeys`:
the initial stock, and the stock after each operation, covering that operation and everything
before it). Simulating a setup again after a change starts from the setup's latest simulation
(`SimulationOptions::resumeFrom`): its initial stock and its leading operations whose keys are
unchanged are taken as they are, and only the operations from the first changed one on are
simulated again (then the comparison). A setup whose stock comes from an earlier setup starts
from that setup's simulation (DL-0012). `kSimulationCacheVersion` 2 stores the keys.

## Consequences

- Posting reuses the toolpaths on screen: the flange posts in under a second, where it took
  157 s generating every operation again (with a wait cursor and no way to cancel). Operations
  not generated yet are generated with a progress dialog that can cancel the post.
- Reopening a saved project shows its toolpaths at once, and rest machining no longer generates
  the operations before it again. On the flange, generating everything went from 100 s to 56 s
  even without a saved cache.
- Whoever changes what a strategy outputs for the same inputs bumps `kToolpathRevision` (in
  `Generate.hpp`). Forgetting it shows stale toolpaths until the next version.
- Saving also writes the toolpaths: larger files (the toolpath JSON compresses well) and a
  slightly slower save.
- The cache is saved only when the project is saved. Opening a project, generating and closing
  it without saving leaves the file as it was.
- Reopening the flange shows its in-process stock in under a second per setup (reading 12 to
  15 MB), where simulating took two and nine minutes. A project opened on another machine, or
  after the local cache was cleared, simulates its setups once in the background.
